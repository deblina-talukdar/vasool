# Prompts used to build and fix the prototype

These were pasted into Google AI Studio Build mode. The first is a summary of the master prompt's intent; the rest are the fix prompts, lightly shortened.

## 1. Master prompt (intent)

Plain accounting-software look (system font, 14px body text, one blue accent, no gradients, no emoji). Indian number and date formats (Rs 6,82,700; "9 Oct 2026"). Six screens: Overview, Follow-ups, Replies, Collected, Activity, Settings. Gemini limited to two jobs: reply-to-JSON (intent, confidence, amount, date) and message drafting, with a clear fallback if a call fails. Key held server-side only.

## 2. Reply-screen fixes

Only treat a number as an amount if it has a currency marker (Rs, rupees, INR) or the customer is clearly quoting a payment figure. Quantities like "2 boxes", "5 days" or "10 pieces" are NOT amounts. If no currency amount is present, set amount to null and show "None mentioned".

The invoice dropdown must list only unpaid invoices (overdue, due soon, disputed, part-paid), sorted by days overdue. Default-select the most overdue one. Never show "0d late" for an invoice that is not overdue.

## 3. Model overload handling

In server.ts, use a Flash-Lite model first. If that call fails with 503 or 429, retry once on the main Flash model before using the fallback.

## 4. Payment link (test mode)

For invoice INV-1016 only, append the Razorpay test-mode payment link to the drafted message and show it as a "Pay balance" button on its Follow-ups card (outstanding balance Rs 98,000). For every other invoice show "Payment link generated by Razorpay once connected". Do not add API keys or server calls for this. Keep amounts coming from invoice data.

## 5. Message preview fixes

For INV-1016 show the payment link only once. When the channel is Voice call, show only the voice-call script. Never show markdown asterisks in a message preview.

## 6. Honest labelling and consistency

- The Follow-ups tab badge and the list header must show the same number, from one shared calculation (exclude do-not-contact, never-auto-contact, disputed, and max-reminder invoices).
- Never show the literal text "null" or "undefined" in the UI.
- Collected screen: "Illustrative figures from synthetic sample data. Not real merchant results."
- Replies screen: "Prototype: replies are pasted here. In production they would arrive from WhatsApp or SMS."
- After Send: "Reminder approved and queued (prototype: nothing is actually sent)", logged in Activity.
- "Reset demo data" must fully restore the original state.
- Use the outstanding balance for part-paid invoices everywhere, including the Activity log.

## 7. Razorpay-inspired theme

Navy #132644 (header, headings), primary blue #305EFF (buttons, active tab), light blue #4D7FFF (accents), soft tint #EAF0FF (selected rows), page background #F0F4F6, white cards with a 1px #DFE3E9 border, muted status colours, contrast at least 4.5:1. Layout, fonts and behaviour unchanged.

## 8. System status tab

Add a "System status" tab after Settings with a real health check: a GET /api/health endpoint that makes one tiny live model call using the same model constant and server-side key, measures latency, retries up to twice on 503 or 429, and returns healthy, degraded or down. The tab shows a coloured dot and label, the model id, last response time and last checked time, refreshes every 60 seconds and has a "Check now" button. Never fake a value; never return the key or raw error bodies.

## 9. Later changes

Razorpay logo in the header, a dynamic "today" date with sample data offset from it, and a dark theme (dark navy backgrounds, lighter cards, light text, readable status colours, logo on a white pill).
